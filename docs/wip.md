# 尚未实现的能力

本文件记录等候上游或后续版本落地的部分。

## 出站引用回复段

**状态：** 不实现，出站消息里的引用回复段会被丢弃，只发送其余段。

**行为：**

- 麦麦回复中若带有引用（reply）段，插件在编码出站消息时把它丢掉，其余段照常发送。
- 若整条回复只有引用段、丢掉后没有可发送的内容，这一次发送直接失败，错误信息为
  `出站消息没有可发送的段`，宿主会看到发送失败而不是一条空消息。
- 被丢弃的段会记进日志，并出现在网关返回值的 `metadata.dropped_segments` 中。

**原因：** 这是上游 Flandora 的限制，不是本插件可以绕过的。Flandora 的出站链路会跳过
引用段：`flandora/ob_protocol.py` 在动作处理里对 `Reply` 段记 `[OB11] 跳过 reply 段` 并计入
`skipped`；只发引用段时整条请求返回 `status=failed`、`retcode=1404`（未实现）。Flandora 自己
把这条列在 `docs/wip.md`（「引用回复段 `reply`：跳过该段，正文照常发送；只发 `reply` 时整条
返回 `retcode=1404`」），原因是微信桌面端无法按 `message_id` 构造引用关系，可能的出路是右键
菜单里的「引用」，仍需真机确认，见其 `docs/needs-user.md` 第 5 节。

**入站方向的引用是正常的：** 微信里引用机器人自己发出的消息时，Flandora 在事件上带
`reply_to_self: true`（正文与消息段不改写），插件据此把这一条按「被提及」处理，麦麦会被唤醒；
被引消息的 `message_id` 也如实传进来。只有「麦麦去引用别人」这个方向不成立。

## 后续版本计划

- **引用块原文**：入站 `reply` 段填 `target_message_id`，唤醒由 `reply_to_self` 承载；
  按 `message_id` 调 `get_msg` 把被引原文与发言人补进 reply 段，排在后续版本。
- **出站 http(s) 链接附件**：Flandora 的发送侧只接受本机路径与 base64，
  网络附件由麦麦侧先落盘成路径或字节再传入。
- **群管理、好友管理、消息撤回、合并转发与 @全体**：随上游 Flandora 落地后在本插件暴露。
- **`video` 段**：目前给文本占位；Flandora 的发送侧已能投递视频文件，后续版本在入站方向转成文件段搬运。
- **`message_sent` 事件**：承载「在 Flandora 面板里替机器人发的消息」，当前不上抛给麦麦；
  后续版本视需要再评估它的入口。
- **部署形态**：当前按麦麦与 Flandora 同机设计，跨机部署排在后续版本。
